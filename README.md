# Stellar — AI Business Operating System

[![Deploy on Railway](https://railway.com/button.svg)](https://railway.com/deploy/TEMPLATE_CODE)

Deploy a complete, self-hosted business operating system on Railway in one click.
Stellar runs as a prebuilt Docker image and connects to **your own Supabase
project** for Postgres, Auth, and Storage.

> **Maintainers:** replace `TEMPLATE_CODE` in the button above with the code
> generated by `railway templates publish`.

---

## What is Stellar?

Stellar is an AI-powered business operating system for small and mid-sized
companies. It combines day-to-day ERP workflows with AI agents that help teams
plan, forecast, reconcile, and report.

### Included modules

- **Dashboard** — business performance overview and analytics.
- **Products & product categories** — catalog and inventory foundations.
- **Contacts** — companies, contacts, and customers.
- **Expenses & expense categories** — spend tracking and categorisation.
- **Quotes, invoices, and payments** — the full invoicing flow.
- **Reports** — ledger, outstanding balances, open invoices, and open quotes.
- **PDF Grid** — configurable PDF generation.
- **Preferences** — currencies, banks, branches, payment modes, and taxes.
- **User management** — application users and access.
- **RBAC** — roles, permissions, and audit logging.
- **Translations** — English and Urdu content management.
- **Supabase Storage** — public and private file management.
- **AI agents** — sales coach, pricing intelligence, forecasting, anomaly
  detection, budget guardian, CEO dashboard, quotation, regulatory, upsell, and
  more.

### Platform features

- Next.js 16 App Router, React 19, and Tailwind CSS 4.
- Supabase Auth with email/password sign-in and password reset.
- Runtime-resolved `NEXT_PUBLIC_*` configuration: change Railway variables
  without rebuilding the image.
- Idempotent pre-deploy migrations, RBAC seed, root-admin bootstrap, and storage
  bootstrap.
- Public, versioned image on GitHub Container Registry.
- Non-root container with a health endpoint at `/api/health`.

## Architecture

```text
                    ┌─────────────────────────────────────┐
                    │              Railway                │
                    │                                     │
  User ──HTTPS──▶   │  main service                       │
                    │  ghcr.io/app-corp/stellar:1.0.0     │
                    │                                     │
                    │  pre-deploy:                        │
                    │    prisma migrate deploy            │
                    │    RBAC seed                        │
                    │    root admin bootstrap             │
                    │    Supabase storage bootstrap       │
                    └───────────────┬─────────────────────┘
                                    │
                                    │ DATABASE_URL / DIRECT_URL
                                    │ Supabase URL + anon/service keys
                                    ▼
                    ┌─────────────────────────────────────┐
                    │         Your Supabase project       │
                    │                                     │
                    │  Postgres  ◀── Prisma               │
                    │  Auth      ◀── sessions, reset      │
                    │  Storage   ◀── public/private files │
                    └─────────────────────────────────────┘
```

There is **no Railway Postgres service**. Supabase is the database, auth
provider, and object store.

## Prerequisites

You need:

- A [Railway](https://railway.com) account.
- A [Supabase](https://supabase.com/dashboard) project.
- A domain (optional; Railway provides one).

From Supabase you will copy:

| Value | Where |
| --- | --- |
| Project URL | Project Settings → API |
| `anon` public key | Project Settings → API |
| `service_role` secret key | Project Settings → API |
| Session-pooler connection string | Connect → Session pooler (port `5432`) |

The service-role key is server-side only. Never expose it to the browser or
commit it.

## Supabase setup

### 1. Create the project

1. Create a Supabase project in a region close to your Railway region.
2. Save the database password.

### 2. Copy API credentials

From **Project Settings → API**:

- Project URL
- `anon` public key
- `service_role` secret key

### 3. Choose the database connection

Railway egress is IPv4. Use the Supabase **Session pooler**:

```text
postgresql://postgres.<project-ref>:<password>@<pooler-host>:5432/postgres?sslmode=require
```

- Copy the full host from the Supabase **Connect** dialog; do not construct it
  from the region.
- URL-encode reserved characters in the password (`@`, `#`, `?`, `&`, spaces).
- The template uses this same value for `DATABASE_URL` and `DIRECT_URL`.

Why not the direct connection? Supabase's direct endpoint is IPv6 unless the
project has the IPv4 add-on. The shared session pooler is IPv4 on every plan and
supports what Prisma migrations need.

If you prefer serverless-style transaction pooling:

```text
DATABASE_URL=postgresql://postgres.<project-ref>:<password>@<pooler-host>:6543/postgres?pgbouncer=true&sslmode=require
DIRECT_URL=postgresql://postgres.<project-ref>:<password>@<pooler-host>:5432/postgres?sslmode=require
```

Do not use transaction pooling for migrations.

### 4. Configure Auth URLs

After Railway gives you a domain, open **Authentication → URL Configuration**:

- **Site URL**
  ```text
  https://<your-railway-domain>
  ```
- **Redirect URLs**
  ```text
  https://<your-railway-domain>/auth/confirm
  https://<your-railway-domain>/auth/reset-password
  ```

If you add a custom domain, update all three values.

### 5. Configure email (recommended for production)

Supabase's built-in mailer is rate-limited. Under **Authentication → Emails**,
configure custom SMTP and verify your sender domain. The root admin is created
with a confirmed email, but password resets depend on email delivery.

### 6. Storage

The pre-deploy step creates the buckets and uploads the default assets:

| Bucket | Visibility | Contents |
| --- | --- | --- |
| `erpblobPublic` | Public | logo, PDF fonts, public assets |
| `erpblob` | Private | private uploads and generated documents |

You can rename them with `NEXT_PUBLIC_SUPABASE_PUBLIC_BUCKET` and
`NEXT_PUBLIC_SUPABASE_PRIVATE_BUCKET`.

### 7. Optional: dedicated Prisma role

Using the `postgres` user works. For better isolation, create a Prisma role in
the Supabase SQL editor:

```sql
create user "prisma" with password '<strong-password>' bypassrls createdb;
grant "prisma" to "postgres";

grant usage on schema public to prisma;
grant create on schema public to prisma;
grant all on all tables in schema public to prisma;
grant all on all routines in schema public to prisma;
grant all on all sequences in schema public to prisma;
alter default privileges for role postgres in schema public grant all on tables to prisma;
alter default privileges for role postgres in schema public grant all on routines to prisma;
alter default privileges for role postgres in schema public grant all on sequences to prisma;
```

Then use `prisma.<project-ref>` as the pooler username.

## Deploy on Railway

1. Click **Deploy on Railway**.
2. Fill in:

   | Variable | Value |
   | --- | --- |
   | `NEXT_PUBLIC_SUPABASE_URL` | `https://<project-ref>.supabase.co` |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase anon key |
   | `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY` | Supabase service-role key |
   | `DATABASE_URL` | Supabase session-pooler string |
   | `BOOTSTRAP_ADMIN_EMAIL` | Your root admin email |
   | `BOOTSTRAP_ADMIN_PASSWORD` | Your root admin password |

3. Click **Deploy**.
4. Wait for the pre-deploy logs:

   ```text
   ✔ release complete
   ✔ root admin ready: <your email>
   ```

5. Open the Railway domain and sign in with the admin credentials.
6. Change the password immediately.
7. Create users in **User Management** and grant roles in **RBAC**.

The first deploy runs migrations against your Supabase database. If the
pre-deploy fails, the new container is not switched in.

## Environment variables

The template prompts for six values and derives the rest with Railway reference
variables.

### Prompted

| Variable | Notes |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | No trailing slash |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Public key |
| `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY` | Sealed; server-side only |
| `DATABASE_URL` | Sealed; Supabase session pooler |
| `BOOTSTRAP_ADMIN_EMAIL` | Root admin login |
| `BOOTSTRAP_ADMIN_PASSWORD` | Sealed; root admin password |

### Derived

| Variable | Value |
| --- | --- |
| `SUPABASE_SERVICE_ROLE_KEY` | `${{NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY}}` |
| `NEXT_PUBLIC_SUPABASE_STORAGE_URL` | `${{NEXT_PUBLIC_SUPABASE_URL}}/storage/v1/object` |
| `NEXT_PUBLIC_SUPABASE_PUBLIC_BUCKET` | `erpblobPublic` |
| `NEXT_PUBLIC_SUPABASE_PRIVATE_BUCKET` | `erpblob` |
| `DIRECT_URL` | `${{DATABASE_URL}}` |
| `NEXT_PUBLIC_APP_DOMAIN` | `https://${{RAILWAY_PUBLIC_DOMAIN}}` |
| `NEXT_PUBLIC_BASE_URL` | `${{NEXT_PUBLIC_APP_DOMAIN}}` |
| `NEXT_PUBLIC_API_URL` | `${{NEXT_PUBLIC_APP_DOMAIN}}` |
| `NEXT_PUBLIC_APP_LOGO` | `${{NEXT_PUBLIC_SUPABASE_STORAGE_URL}}/public/${{NEXT_PUBLIC_SUPABASE_PUBLIC_BUCKET}}/assets/stellar-app-logo.webp` |
| `NEXT_PUBLIC_APP_NAME` | `Stellar App` |

If your Railway workspace does not resolve nested references, enter the derived
values explicitly.

### Optional

| Variable | Purpose |
| --- | --- |
| `GOOGLE_GENERATIVE_AI_API_KEY` | Google AI agents |
| `REPLICATE_API_TOKEN` | Replicate image generation |
| `NEXT_PUBLIC_PEXELS_API_KEY` | Pexels image search |
| `NEXT_PUBLIC_APP_DOMAIN` | Custom domain; overrides the Railway domain |
| `BOOTSTRAP_ADMIN_RESET_PASSWORD` | `true` to force a password rotation on the next deploy |

`NEXT_PUBLIC_*` values are resolved at runtime, so changing them does not
require an image rebuild.

## What happens during deploy

Railway runs the pre-deploy phase before switching traffic:

```text
node migrate/release.mjs
  → prisma migrate deploy          apply pending SQL migrations
  → seed RBAC roles and permissions
  → create/update the root admin
  → create Supabase buckets and upload default fonts/logo
```

Every step is idempotent. A failure stops the deployment before users see a
broken app.

Then the container starts:

```text
node apps/main/server.js
```

on Railway's `PORT` (default 3000).

### Root admin behaviour

- The configured `BOOTSTRAP_ADMIN_EMAIL` is promoted to `admin` even if other
  admins exist.
- Other accounts are never auto-promoted; grant roles from the RBAC screen.
- If the bootstrap email is unset, the legacy fallback promotes the first
  authenticated user only when no admin exists. Do not rely on this in
  production.

## After deployment

- Change the root admin password from the profile page.
- Create application users in **User Management**.
- Grant roles and permissions in **RBAC**.
- Upload your logo/assets to the public bucket, or keep the defaults.
- Configure custom SMTP in Supabase for password-reset email.
- Review Supabase plan limits and enable backups if available.

### Custom domain

1. Railway → service → **Settings → Networking** → add the domain.
2. Set `NEXT_PUBLIC_APP_DOMAIN` to `https://<your-domain>`.
3. Update Supabase Auth Site URL and redirect URLs.
4. Redeploy.

## Updates and rollback

The template pins a full image version, for example
`ghcr.io/app-corp/stellar:1.0.0`, and enables Railway image auto-updates for
**minor and patch** releases. Railway moves the service to `1.0.x` / `1.x`
during the configured maintenance window.

- **Pin a version:** change the service image to
  `ghcr.io/app-corp/stellar:<version>`.
- **Disable auto-updates:** turn them off in the service settings.
- **Rollback:** set the image to the previous semver tag and redeploy. Keep
  migration compatibility in mind; database migrations are forward-only.
- **Major releases:** update the template/service image reference; they are not
  auto-applied.

Image tags published by CI:

```text
1.2.3       full release
1.2         minor channel
1           major channel
latest      latest main build
sha-<commit> immutable commit build
```

Because this template uses a Docker image source, Railway template update
notifications do not apply. Image auto-updates are the update mechanism.

## Operations

### Health

```text
GET /api/health  → 200 {"status":"ok"}
```

Railway uses this for the deployment healthcheck.

### Logs

Watch the pre-deploy logs for migration, seed, admin, and storage output. The
runtime logs show Next.js requests and API errors.

### Scaling and connections

- Start with **one replica**.
- Supabase pooler connection limits depend on your plan. If you scale replicas,
  account for the app's connection pool per instance.
- The app is stateless; no Railway volume is required.

### Security

- Keep the service-role key and database password in Railway sealed variables.
- Do not commit `.env` files.
- Use Supabase Auth redirect allowlists; do not leave wildcards.
- Enable RLS on tables exposed through the Supabase Data API. Stellar uses
  Prisma, so the Data API is optional.
- Configure SMTP and verify your sender domain.
- Back up the database regularly; Supabase Pro provides automated backups.

## Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| `P1001` / database timeout | Use the Supabase **Session pooler** (port `5432`), not the direct IPv6 connection. |
| `prepared statement "s0" already exists` | Transaction pooler without `pgbouncer=true`. Use the session pooler. |
| Migration authentication failure | URL-encode the password; confirm `DIRECT_URL` uses the session pooler. |
| Pre-deploy fails on storage | Check the service-role key and `migrate/bootstrap-storage.mjs` logs. Buckets are `erpblobPublic` and `erpblob`. |
| Login works but no menu / 403 | Sign in with the configured `BOOTSTRAP_ADMIN_EMAIL`; sign out and back in to refresh permissions. |
| Password-reset link points to the wrong host | Set `NEXT_PUBLIC_BASE_URL` and Supabase Auth Site URL to the Railway/custom domain. |
| Uploads fail | Check storage bootstrap and bucket names; verify the service-role key. |
| PDF fonts fail | The public bucket must contain `fonts/inter-*.ttf`; re-run the pre-deploy. |
| Railway cannot pull the image | The GHCR package must be public. Maintainers: package settings → Change visibility → Public. |
| Logo shows `stellarapp.site` or demo images | Some demo content still references the public demo bucket. Replace those assets/URLs for a fully white-labelled deployment. |

## For template maintainers

- Template source project: `.railway/railway.ts` in the deployment repository.
- Image: `ghcr.io/app-corp/stellar:1.0.0` with image auto-updates `minor`.
- Pre-deploy: `node migrate/release.mjs`.
- Healthcheck: `/api/health` with a 120s timeout.
- Variables are configured in the Railway template composer, not in the IaC
  file.

Publish/update the template:

```bash
railway login
railway link
railway config plan
railway config apply --yes

railway templates create --project stellar-public --json
railway templates publish <template-id> \
  --category "AI/ML" \
  --description "Stellar AI Business Operating System" \
  --readme-file README.md \
  --json
```

to GHCR, creates a GitHub Release, and verifies the package is public. See
