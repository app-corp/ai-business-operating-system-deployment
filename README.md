# Stellar — AI Business Operating System

[![Deploy on Railway](https://railway.com/button.svg)](https://railway.com/deploy/TEMPLATE_CODE)

Deploy a self-hosted business operating system on Railway in one click. Stellar
runs as a prebuilt Docker image and connects to **your own Supabase project** for
Postgres, Auth, and Storage.

> **Maintainers:** replace `TEMPLATE_CODE` with the code generated by
> `railway templates publish`.

## What you get

- **ERP:** dashboard, products, contacts/customers, expenses, quotes, invoices,
  payments, reports, PDF grid, preferences, user management, RBAC, translations,
  and file storage.
- **AI agents:** sales coach, pricing intelligence, forecasting, anomaly
  detection, budget guardian, CEO dashboard, quotation, regulatory, upsell, and
  more.
- **Platform:** Next.js 16, React 19, Supabase Auth, runtime-resolved
  `NEXT_PUBLIC_*` variables, non-root container, `/api/health`.
- **Automated deploy:** Prisma migrations, RBAC seed, root-admin bootstrap, and
  Supabase bucket/asset setup run before traffic switches.

## Architecture

```text
User ──HTTPS──▶ Railway service ──▶ Supabase
                ghcr.io/app-corp/stellar:1.0.0
                pre-deploy: migrate + seed + admin + storage
                                   ├─ Postgres (Prisma)
                                   ├─ Auth
                                   └─ Storage (public/private)
```

No Railway Postgres service is used.

## Prerequisites

- [Railway](https://railway.com) account.
- [Supabase](https://supabase.com/dashboard) project.
- Optional custom domain.

From Supabase: **Project URL**, **anon key**, **service-role key**, and a
**Session pooler** connection string (Connect → Session pooler, port `5432`).

## Supabase setup

### 1. Project and keys

Create a project near your Railway region. Save the database password. From
**Project Settings → API**, copy the project URL, anon key, and service-role key.
Keep the service-role key server-side only.

### 2. Database connection

Use the **Session pooler** (IPv4, port `5432`):

```text
postgresql://postgres.<project-ref>:<password>@<pooler-host>:5432/postgres?sslmode=require
```

Copy the full host from Supabase; do not construct it from the region.
URL-encode reserved password characters. This value is used for both
`DATABASE_URL` and `DIRECT_URL`.

The direct connection is IPv6 unless you have the IPv4 add-on. For transaction
pooling, use port `6543` with `pgbouncer=true` for `DATABASE_URL`, and keep the
session pooler for `DIRECT_URL`. Never use transaction pooling for migrations.

### 3. Auth URLs

After Railway assigns a domain, set **Authentication → URL Configuration**:

- Site URL: `https://<your-domain>`
- Redirect URLs:
  - `https://<your-domain>/auth/confirm`
  - `https://<your-domain>/auth/reset-password`

Update these again if you add a custom domain.

### 4. Email

Supabase's built-in mailer is rate-limited. For production, configure custom
SMTP under **Authentication → Emails** and verify the sender domain.

### 5. Storage

The pre-deploy creates the buckets and uploads the default logo and PDF fonts:

| Bucket | Visibility | Contents |
| --- | --- | --- |
| `erpblobPublic` | Public | logo, fonts, public assets |
| `erpblob` | Private | private uploads, generated documents |

Rename them with `NEXT_PUBLIC_SUPABASE_PUBLIC_BUCKET` and
`NEXT_PUBLIC_SUPABASE_PRIVATE_BUCKET`.

### 6. Optional Prisma role

Using `postgres` works. For isolation, create a Prisma role in the SQL editor:

```sql
create user "prisma" with password '<strong-password>' bypassrls createdb;
grant "prisma" to "postgres";
grant usage on schema public to prisma;
grant create on schema public to prisma;
grant all on all tables in schema public to prisma;
grant all on all routines in schema public to prisma;
grant all on all sequences in schema public to prisma;
alter default privileges for role postgres in schema public grant all on tables to prisma;
alter default privileges for role postgres in schema public grant all on routines to prisma;
alter default privileges for role postgres in schema public grant all on sequences to prisma;
```

Use `prisma.<project-ref>` as the pooler username.

## Deploy

1. Click **Deploy on Railway**.
2. Fill in:
   - `NEXT_PUBLIC_SUPABASE_URL`
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY`
   - `DATABASE_URL` (session-pooler string)
   - `BOOTSTRAP_ADMIN_EMAIL`
   - `BOOTSTRAP_ADMIN_PASSWORD`
3. Deploy and watch the pre-deploy logs for:
   ```text
   ✔ release complete
   ✔ root admin ready: <email>
   ```
4. Set the Supabase Auth Site URL/redirects (step 3 above).
5. Sign in, change the admin password, then create users and grant roles in
   **User Management** and **RBAC**.

If pre-deploy fails, the new container is not switched in.

| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | No trailing slash |

| `NEXT_PUBLIC_APP_DOMAIN` | `https://${{RAILWAY_PUBLIC_DOMAIN}}` |
| `NEXT_PUBLIC_BASE_URL` | `${{NEXT_PUBLIC_APP_DOMAIN}}` |
| `NEXT_PUBLIC_API_URL` | `${{NEXT_PUBLIC_APP_DOMAIN}}` |

If nested references are not supported, enter the derived values explicitly.

### Optional

`GOOGLE_GENERATIVE_AI_API_KEY`, `REPLICATE_API_TOKEN`,
`NEXT_PUBLIC_PEXELS_API_KEY`, `NEXT_PUBLIC_APP_DOMAIN` (custom domain), and
`BOOTSTRAP_ADMIN_RESET_PASSWORD=true` (force password rotation).

`NEXT_PUBLIC_*` values are runtime-resolved; changing them does not require an
image rebuild.

## Pre-deploy

```text
node migrate/release.mjs
  → prisma migrate deploy
  → seed RBAC roles and permissions
  → create/update root admin
  → create buckets and upload fonts/logo
```

Every step is idempotent. The container then starts with
`node apps/main/server.js` on Railway's `PORT`.

The configured `BOOTSTRAP_ADMIN_EMAIL` is always promoted to `admin`; other
accounts are never auto-promoted. Do not rely on the legacy first-user fallback
in production.

## After deploy

- Change the root admin password.
- Create users and assign roles.
- Upload your logo/assets or keep the defaults.
- Configure SMTP and review Supabase plan limits/backups.
- Optional custom domain: add it in Railway, set `NEXT_PUBLIC_APP_DOMAIN`, update
  Supabase Auth URLs, and redeploy.

## Updates and rollback

The template pins `ghcr.io/app-corp/stellar:1.0.0` and enables Railway image
auto-updates for minor/patch releases.

Tags: `1.2.3`, `1.2`, `1`, `latest`, `sha-<commit>`.

- Pin a version by changing the service image tag.
- Disable auto-updates in service settings.
- Roll back by setting the previous tag; migrations are forward-only.
- Major releases are not auto-applied.

Docker-image templates do not receive Railway template update notifications;
image auto-updates are the update mechanism.

## Troubleshooting

| Symptom | Fix |
| --- | --- |
| `P1001` / DB timeout | Use the Supabase Session pooler (port 5432), not direct IPv6. |
| `prepared statement "s0" already exists` | Transaction pooler without `pgbouncer=true`; use session pooling. |
| Migration auth failure | URL-encode the password; confirm `DIRECT_URL` uses the session pooler. |
| Storage bootstrap fails | Check the service-role key and `bootstrap-storage.mjs` logs. |
| Login works but menu empty / 403 | Sign in with `BOOTSTRAP_ADMIN_EMAIL`; sign out and back in. |
| Reset link has wrong host | Set `NEXT_PUBLIC_BASE_URL` and Supabase Auth Site URL. |
| Uploads fail | Check buckets `erpblobPublic`/`erpblob` and the service-role key. |
| PDF fonts fail | Public bucket must contain `fonts/inter-*.ttf`; re-run pre-deploy. |
| Railway cannot pull image | GHCR package must be public. |
| Demo images use another host | Some marketing content still points at the public demo bucket; replace for white-labelling. |
